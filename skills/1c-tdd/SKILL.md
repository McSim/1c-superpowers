# Эталон до кода (1c-tdd)

Предмет — изменение поведения в BSL/XML, у которого есть чем доказать результат. Цикл «красный → зелёный» — не обязательный ритуал: обязателен **эталон, зафиксированный до кода**, и он не обязан быть тестом.

## Когда открывать

- Новая или меняющаяся логика: проведение, расчёт, обменный контур, общий модуль.
- Роутер направил по «сначала тест», «TDD», «напиши тест», «Vanessa», «YAxUnit».
- `1c-executing-plans` в задаче явно требует проверяемого поведения.

Не открывать для косметического переименования без смены поведения — достаточно синтаксиса и review по diff.

## Шаги по порядку

1. **Артефакт и критерий.** Что должно быть видно снаружи: документ проводится, движения Дт/Кт с суммами, числа отчёта, статус обмена, поведение формы. Критерий берётся из задачи, ТЗ или слов заказчика, **не из будущей реализации**.
2. **Шлагбаум репо.** `python3 <каталог 1c-verification>/scripts/find_checks.py <корень проекта>`.
   - Метка «можно запускать сценарии (TDD)» с Vanessa / `.feature` — **ветка VA**.
   - Метка с YAxUnit / `tests/Test*.bsl` / `yaxunit.json` — **ветка YAxUnit**.
   - Меток нет — **ветка факта цели**, это не стоп.
   - `vanessa-runner.json` / `env.json` с меткой «не запускать из ревью» — из review базу не грузить; для эталона — только известная команда проекта.
3. **Эталон.** Выбрать один и записать до кода: вход, ожидаемый результат, чем наблюдаем.
   - **Факт цели (по умолчанию, если артефакт есть)** — наблюдаемый результат в базе: документ проводится, движения Дт/Кт/суммы, отчёт даёт числа, пакет обмена принят.
   - **Тест или сценарий не этого агента** — человек, другой агент или готовый тест в репо. Только здесь уместен красный → зелёный.
   - **Репро на дефект** — падающий сценарий, воспроизводящий баг; его авторство тоже не этого прогона.
4. **Код.** Минимальный diff в границах задачи плана.
5. **Проверка.** Прогнать эталон. Для факта цели — реальный путь в базе или её копии (`1c-headless-run`: COM, ibcmd), до и после.
6. **Передача.** В `1c-executing-plans`; перед сдачей — `1c-verification`, сводка — `1c-review`. Зелёный прогон закрывает **этот** эталон, не весь MR.

## Ветка VA

1. Команда прогона из README/CI (не выдумывать).
2. Красный → минимальный BSL → зелёный.
3. В ответе: команда, код возврата, хвост лога.

## Ветка YAxUnit

1. Команда из README/CI: `1cv8c ENTERPRISE /IBName <база> /N <пользователь> /C RunUnitTests=<yaxunit.json>`; расширение YAxUnit в базе без безопасного режима. Свою команду не изобретать.
2. Красный тест (или новый тест на поведение) → минимальный production-код → зелёный.
3. Не подменять Vanessa-сценарием, если в репо только YAxUnit, и наоборот.

## Ветка факта цели (по умолчанию)

Тест-фреймворка нет — это не повод останавливаться: у проведения, отчёта и обмена факт обычно есть.

1. Согласовать наблюдаемый результат: что именно должно быть видно (проведение без ошибок, конкретные Дт/Кт/суммы, числа отчёта, статус пакета).
2. Записать вход: документ, дата, организация, суммы.
3. Получить результат в базе или копии и сравнить с ожидаемым; сохранить «до/после».
4. Ожидаемый результат не согласован — **стоп**, один вопрос: что считается результатом.

## Стоп и запреты

- **Тест, выведенный из этой же реализации, — не доказательство.** Он наследует её ошибки и зеленеет вместе с ними: тесты по спецификации ловят около 25% внедрённых дефектов, тесты после кода — около 14% (arXiv:2607.05139). Оракул должен быть независим: спецификация, артефакт, чужой тест или другой агент.

- **Красный, который увидел тот же агент, что написал тест, — не доказательство.** Он подтверждает запуск, а не что тест ловит нужное поведение. Red-green уместен, только когда эталон написал **не этот же агент**: человек, другой агент или готовый тест в репо.
- Нет оракула (эталона) и нет согласованного факта цели — **стоп**; production-код «на глаз» не писать.
- Зелёный тест ≠ вердикт сдачи (`1c-review`).
- Не расширять scope чужими модулями.
- Не запускать из ревью то, что помечено «не запускать из ревью».

## Что отдать

- **1c-executing-plans / человеку:** эталон (VA, YAxUnit или факт цели), что наблюдали, команда.
- **1c-review:** diff после verify, если затронуты проведение, обмен или CFE.
